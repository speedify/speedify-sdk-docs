Implementing AutoConstruct

In your Application class, implement SpeedifySDK.AutoConstruct:

// Implement SpeedifySDK.AutoConstruct
class MyApplication : Application(), SpeedifySDK.AutoConstruct {

  // ...

  override fun getSpeedifySDK(context: Context): SpeedifySDK {
    // instantiate a new SDK object
    val sdk = SpeedifySDK(context, "My App Title", object : SpeedifyHandler() {
      // override wanted methods here
    })

    // If using Dispatch, add on the Dispatch library
    Dispatch.getInstance(context)

    // If using Enhanced Statistics, add on the Enhanced Statistics library
    EnhancedStatistics.getInstance(context)

    return sdk
  }

  // ...

}

// Implement SpeedifySDK.AutoConstruct
public class MyApplication extends Application implements SpeedifySDK.AutoConstruct {

  // ...

  @Override
  public SpeedifySDK getSpeedifySDK(Context context) {
    // instantiate a new SDK object
    SpeedifySDK sdk = new SpeedifySDK(context, "My App Title", new SpeedifyHandler() {
      // override wanted methods here
    });

    // If using Dispatch, add on the Dispatch library
    Dispatch.getInstance(context);

    // If using Enhanced Statistics, add on the Enhanced Statistics library
    EnhancedStatistics.getInstance(context);

    return sdk;
  }

  // ...

}

Starting the Speedify SDK

Before you use the Speedify SDK in your app, you must initialize VPN permission.

  // check for vpn permission, and request it if needed
  if (!SpeedifySDK.hasVPNPermission(this)) {
    SpeedifySDK.initializeVPNPermission(this)
  }

  // check for vpn permission, and request it if needed
  if (!SpeedifySDK.hasVPNPermission(this)) {
    SpeedifySDK.initializeVPNPermission(this);
  }

When you want to start the Speedify SDK, call this to get an instance of the SDK.

  val sdk = SpeedifySDK.getInstance(context)

  SpeedifySDK sdk = SpeedifySDK.getInstance(context);

Logging In

You must be logged in before you can connect. A fresh SDK starts in the LOGGED_OUT state; once authenticated it moves to LOGGED_IN, from which you can connect. State changes are delivered to OnState (see Receiving State in Your UI).

Choose one of:

  • login(username, password) — a Speedify account.
  • loginOAuth(token) — an OAuth access token your own backend issued. Only for integrations that manage their own tokens: you supply the token and deliver replacements when it expires, via refreshOAuthToken. This is an enterprise feature that requires additional backend development; contact Connectify for more information about implementing this for your organization.
  • getActivationCode() — activate the device from a browser instead of entering credentials in-app. Useful for TVs, set-top boxes, and other limited-input devices.

How Often to Log In

Logging in is a one-time operation, not something to do on every launch. A successful login stores the credentials in the SDK's secure storage, and the SDK re-authenticates with them by itself every time it starts — after an app restart, an app update, or a device reboot — retrying automatically with backoff when the network is down. Call a login method again only when:

  • the user has never logged in on this device (first run),
  • logout was called — it clears the stored credentials,
  • the stored credentials stop working — OnLoginError reports CREDENTIAL (password changed, account revoked) or TOKEN_EXPIRED — the SDK tried to refresh the token itself and could not, so supply a fresh one via refreshOAuthToken if your backend issues them, and otherwise sign the user in again, or
  • credential storage is disabled with setDoNotStoreCredentials — then nothing persists and every SDK start begins logged out.

The current state is delivered to OnState (call refreshState to fetch it on demand); there is no synchronous state getter.

Do not log in from OnState. The SDK passes through LOGGED_OUT briefly at every startup while its own stored-credential login is in flight, so treating LOGGED_OUT as "ask the user to sign in" prompts them on every launch. Sign in from your own UI on first run, and let OnLoginError tell you when the stored credentials have stopped working:

  override fun OnLoginError(errorType: Types.ErrorType?, message: String?) {
    when (errorType) {
      // the stored credentials no longer work: show your sign-in UI again
      Types.ErrorType.CREDENTIAL -> showSignIn()
      // The SDK already tried to refresh this token and could not, whoever
      // issued it. If your own backend issues them, hand over a new one with
      // refreshOAuthToken; otherwise the user has to sign in again.
      Types.ErrorType.TOKEN_EXPIRED -> showSignIn()
      // anything else is usually transient; the SDK retries with backoff
      else -> { }
    }
  }

  @Override
  public void OnLoginError(Types.ErrorType errorType, String message) {
    if (errorType == Types.ErrorType.CREDENTIAL) {
      // the stored credentials no longer work: show your sign-in UI again
      showSignIn();
    } else if (errorType == Types.ErrorType.TOKEN_EXPIRED) {
      // The SDK already tried to refresh this token and could not, whoever
      // issued it. If your own backend issues them, hand over a new one with
      // refreshOAuthToken; otherwise the user has to sign in again.
      showSignIn();
    }
    // anything else is usually transient; the SDK retries with backoff
  }

The activation-code flow is a two-step login. Call getActivationCode, then handle OnActivationCode, which delivers an activationCode and an activationUrl. Present those to the user (for example, render the URL as a QR code); they open the URL in a browser, sign in, and enter the code to authorize this device. On success the SDK transitions to LOGGED_IN like any other login — watch OnState.

Login failures are reported via OnLoginError. If login fails even with valid credentials, confirm your app has been authorized — see Prerequisites. Call logout to log out.

What the SDK Retries on Its Own

You do not need retry loops around login or connect. The SDK already has them, and a second layer only multiplies traffic when something is actually down.

Login. After a failed login the SDK keeps trying by itself for as long as it holds stored credentials, waiting longer between attempts each time, from seconds at first to a ceiling of tens of minutes. Errors that mean the account or credential itself is the problem (bad credentials, an expired token, rate limiting, an exhausted quota or device limit) back off faster. A successful login resets the schedule, and setMaximumConnectRetry caps the longest wait if the ceiling is too long for your product.

Every attempt that fails, including the automatic ones, reaches OnLoginError. Expect the same CREDENTIAL or TOKEN_EXPIRED to arrive again at each retry until you log in with something new or call logout, which clears the stored credentials and stops the retries. Make the handler idempotent: showing your sign-in screen once is right, stacking a dialog per attempt is not.

Connect. A failed connect first falls through to the next candidate server; you see OnConnectedServer for each one tried and no error. When the candidates are exhausted the SDK reports OnConnectError, drops back to LOGGED_IN, and schedules another full attempt on the same backoff as login, passing through AUTO_CONNECTING each time. Each attempt is bounded, so a hung one does not stall the schedule. This continues until it connects, until you call disconnect, or until the server answers with an error that retrying cannot fix. Connecting resets the schedule.

Transport failures on one Internet connection while a session is up are handled separately, per connection, with their own backoff; setMaximumTransportRetry caps that one.

Keeping an OAuth Token Fresh

This section only applies to integrations that issue their own tokens and log in with loginOAuth. With a Speedify account or an activation code the SDK renews its own tokens and there is nothing to do.

The SDK presents the token you gave it on every call to the Speedify backend: at login, at every connect (the server assignment), and in periodic background account refreshes, more frequent while connected than while merely logged in. The tunnel itself does not use the token, so a token expiring mid-session does not end the session by itself; the next backend call does. The SDK cannot renew a token it did not issue, so on that call it reports TOKEN_EXPIRED, logs out (disconnecting if connected), and then retries the login with the token it still holds on the schedule above, reporting TOKEN_EXPIRED again each time, until you hand it a replacement.

So the rule is to deliver the replacement before the current token expires, with refreshOAuthToken. While the SDK is logged in with an OAuth token that call only stores the new token for the next request, with no network round trip and no state change, so it is safe to call as often as your backend rotates tokens. In practice:

  • Issue tokens with lifetimes measured in hours or days, not minutes; the SDK's own background refreshes will otherwise find them expired between yours.
  • Call refreshOAuthToken whenever your backend gives you a new token, and check the held token's expiry when the app comes to the foreground, refreshing if it is in the last quarter of its lifetime.
  • Treat TOKEN_EXPIRED as the sign that this schedule has already failed. Hand over a new token immediately; refreshOAuthToken logs back in at once when the SDK is logged out. Do not wait for the next automatic retry.

Optional: Application onCreate

The Speedify SDK starts up a background process to run the VPN. If you initialize other components in your Application's onCreate, you may need to return early to avoid initializing them in this process as well.

  override fun onCreate() {
    super.onCreate()

    // ... common initialization ...

    if (SpeedifySDK.IsBackgroundProcess(this)) return

    // ... other initialization that you only want to run in your app's UI process ...
  }

  @Override
  public void onCreate() {
    super.onCreate();

    // ... common initialization ...

    if (SpeedifySDK.IsBackgroundProcess(this)) return;

    // ... other initialization that you only want to run in your app's UI process ...
  }

Receiving State

To drive your UI you register an ISdkStateReceiver, whose callbacks run in your process — see Receiving State in Your UI. This is distinct from the SpeedifyHandler below, some of whose callbacks run in the SDK's background process.

Optional: Handlers

If you do not specify a custom SpeedifyHandler in getSpeedifySDK, you can call setHandler on your SpeedifySDK object to set one later. Note that some callbacks on the ISpeedifyHandler happen in Speedify SDK's background process. If you want to implement these, use the SpeedifySDK.AutoConstruct method above.

Optional: Stopping What You Aren't Using

Everything here is safe to stop and start again at any time:

  • Statistics — enableStatUpdates(false, null) stops the once-per-second stats stream. Enable it only while a screen that displays stats is visible; see Receiving State in Your UI.
  • State receivers — sdkStateReceivers.unregister when the UI that was listening goes away.
  • The tunnel — disconnect tears down the VPN but leaves the SDK logged in and its services running, ready to connect again.
  • The SDK itself — SpeedifySDK.ForceExit(context) disconnects, stops the SDK's background VPN process, and removes the foreground service notification. Any SpeedifySDK object you previously constructed becomes unusable after this; to start again, obtain a new SpeedifySDK object or call restartServices on the old one. Stored login credentials are kept, so the SDK logs back in on the next start.
